## 必要修订

### R1：给出唯一决策入口，并确定 HTTP 层迁移的阶段位置（P2）

证据：基线末段明确要求“唯一的最终架构设计入口”“已选技术、渐进迁移范围”。技术补充第 4、9、19、49、54 行仍为“不替换旧高层方案”“候选”；旧 hlplan 的 P0–P3 主要讨论 Orca，未安排 HTTP 层替换的位置。

影响：读者仍需把两份候选方案拼接，无法判断 FastAPI/Uvicorn 是本轮选定的目标技术、可选调查项，还是 P1 的前置条件。下游可能把工作台 HTTP 改造和 Orca 隔离实验捆成一次变更。

修订：创建或明确一个最终架构入口，写清已决定保留、选定但未实施、条件化采用、延期四类。明确 HTTP 层改造与 Orca 验证为两个可独立回退的增量，以及哪个先做。无需在架构文档给出函数签名、安装命令或完整任务表；也不需要把所有技术未知变成用户问题。

### R2：HTTP 框架迁移必须继承现有管理面信任边界（P1）

证据：技术补充第 49–57 行覆盖 ASGI、线程池和单 worker，但未定义现有管理面安全合同的保留边界。实际 `gateway.py:133–150` 对 Host、Origin、客户端标记与敏感操作 CSRF 做检查；`:490–501` 实现 Windows 独占监听和生产 loopback 限制。研究 stability 的 C1 也明确现有这些保护。

影响：选择成熟 HTTP 框架本身不代表保留这些本地安全语义。若下游只迁移业务路由和 async 生命周期，可能把可执行 Agent 操作暴露给不应受信的请求。Orca loopback、配对校验的规定不替代 Python 管理面自己的边界。

修订：最终架构明确管理 API 继续仅本机、保持等价的 Host/Origin/敏感操作防跨站请求及客户端权限规则；现有 Windows 监听独占语义纳入兼容核验。完整 Orca 客户端配对权限与管理页权限保持各自归属；不以连通需要为由默认放宽 CORS 或引入凭证转发。具体中间件和测试用例留到低层设计。此项是保护已存在合同，不是要求新增认证平台。

### R3：固定管理进程和外置 runtime 的生命周期责任（P1）

证据：技术补充第 73 行只明确关页面不停任务，并写“显式停 runtime 的影响必须另有合同”；第 98 行要求运行托管但未指定谁拥有 runtime。原 hlplan P1 要求停止操作后自身进程与监听清理。现有 `gateway.py:481–488` 会在服务关闭时调用 execution.close，后者 `execution.py:244–274` 请求取消并清理 worker。

影响：外置进程不等于独立生命周期。管理服务重启或升级时若仍沿用旧关闭路径，会与新 runtime 持续运行的预期冲突；若改为不清理又无明确所有者，会出现无人负责的进程。架构必须先决定此关系，不能仅让低层作者自行选择。

修订：用简短责任表确定管理服务正常退出/崩溃、runtime 正常退出/崩溃、页面断连、整套应用退出各自影响与事实归属。指定 runtime 的启动/关闭所有者，明确管理服务恢复只做对账、不重发。可以选择人工管理的独立 runtime 作为初期形态，无需立即引入服务管理产品。停止和孤儿清理是否实际成立仍交给后续验证，旧 M3 的关闭行为继续按原合同保留。

### R4：选择首期准入覆盖范围，避免“全局”与完整客户端第二入口并存而无定论（P2）

证据：技术补充第 69–70 行准确识别面板锁只保护面板路径，并给出“共享 runtime 原生控制”或“所有受控派发唯一入口”两个方向；第 78 行又推荐“按全局、Provider、工作目录设置有界准入”。同时目标图与旧 hlplan D2 推荐完整官方客户端作为独立入口。

影响：风险已识别，但最终架构尚未选择首期到底承诺哪一个范围。完整客户端能发起执行时，面板自身的预算不能被用户理解为机器全部 Agent 的预算；这直接影响多 Agent 稳定性目标和目录冲突边界。

修订：明确首期预算仅覆盖面板派发、或选择经核验的 runtime 统一准入。若暂选前者，明确独立客户端/CLI 不纳入该保证，混合派发不能作为受控并发验收场景；若业务需要全局保证，则以 runtime 能力核验为采用门槛，未通过时保持仅入口展示。阈值与锁实现可下沉，覆盖范围不能下沉。此项不要求现在实现额外队列或运行时插件。
