## 完整实现基线

### 1. 目标锁

- G1：形成可审阅的高层方案，明确现有工作台和 Orca 的职责、实际接入面、展示复用方法、底层技术候选、Rust 取舍、多 Agent 并发可靠性与扩展边界；区分当前实现与推荐。
- G2：给出下一项隔离验证的范围、交付物与停止条件，使后续能判断是否值得用 Orca 替代自研执行链；以一手证据区分 Pi/Hermes 等 Agent 的终端入口、结构化控制与未知能力，并给出容量验证方向；不把“服务能启动”当成“审批/取消可用”，不承诺未实测的并发数。
- G3：把像素场景排除出近期接入范围；基于真实代码解释小院业务账本与动画的区别，业务价值不足时延期。

### 2. 反目标

- 不把架构借鉴、静态卡片、动画、Agent CLI 被发现或上游源码存在写成已接入/实时运行/已交付。
- 不为复用之名将整个面板重写为完整 IDE，也不把 Orca 的 TS 代码逐段翻译成新的 Python Provider 框架。
- 不以现有产品不完善为理由增加像素场景、所有 Provider、跨设备部署或自动付费试跑的工作量。

### 3. 风险边界

- 本轮只修改本目录规划文档；不安装、构建、启动 Orca，不发送 Agent 任务，不访问凭证或私人会话正文，不更改公网监听/防火墙/全局配置。
- Windows 前台 runtime、配对认证、事件订阅、结构化审批/取消、Web 构建和展示嵌入均须分别验证；没有验证时只写证据缺口。
- 调研补充：CLI `orca serve` 固定宽监听，`pairing-address` 不能限缩 bind；下一项实验只评估支持显式 loopback 的直接 Node entry，不允许自动 fallback 到宽监听路线。
- 调研补充：Node SecretStore 不继承 Electron 系统加密；独立 profile 也不证明 Provider home/账号隔离。初次实验不导入账号、不读取私人正文，不先做真实模型试跑。
- 旧 M3 状态和历史审查不改写；旧数据库、项目 JSON、garden 收据和自研源码保留。
